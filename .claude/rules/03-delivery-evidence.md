# 交付证据

AI 编码最常见的失败不是写不出代码，而是**"我觉得我做完了"**。这条规则把"完成"从一个感觉变成一个可核验的陈述。

## 声明完成前，必须给出三段式汇报

```
【做了什么】
- 改动文件 + 每个文件改了什么（一句话）

【凭什么说完成了】（必须有实际输出，不能是描述）
- 执行的命令：<原样粘贴命令>
- 实际输出：<原样粘贴输出，含通过/失败计数>
- 覆盖范围：哪些路径被验证到

【还没做的 / 有风险的】
- 未覆盖的场景
- 已知缺陷或妥协
- 需要人工确认的点
```

## 硬性要求

- **"跑过了，通过了"不算证据。** 必须粘贴命令原样输出。
- **没有测试的任务**，至少给出：手动验证步骤 + 你实际观察到的结果。
- **测试失败时不要声称部分完成。** 明说哪条挂了、挂在哪一行。
- **不允许修改测试来让它通过**，除非能说明原测试本身是错的。

## 禁止的措辞

| 不要说 | 改成 |
|---|---|
| "已完成" | "已实现 X，跑了 `pnpm test`，142 通过 0 失败" |
| "应该可以工作" | "已验证 A、B 场景；C 场景未验证" |
| "修复了问题" | "根因是 X，改了 Y，验证方式是 Z" |
| "所有测试通过" | "测试通过，但 coverage 未覆盖错误路径" |

## 顺带清理

完成任务时一并检查：

- 有没有留下临时调试代码、`console.log`、注释掉的代码块
- 有没有留下本次改动的旧的、不再被调用的函数
- 有没有留下 TODO 而没说明它对应什么任务

> 这三条正是"幽灵代码"的来源。0-1 阶段每天清理一次，比三个月后集中重构便宜得多。
