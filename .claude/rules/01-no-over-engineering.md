# 反过度设计

0-1 阶段最大的浪费不是写错，而是**写多了**。错误的抽象一旦落地，后面所有代码都要绕着它走。

## 判定规则

动手前逐条自检，任何一条不满足就**不要做**：

| 你要做的事 | 前提条件 |
|---|---|
| 抽公共函数/模块 | 已有 ≥2 处真实调用点（不是"将来会有"） |
| 定义接口/抽象基类 | 已有 ≥2 个真实实现 |
| 加配置项/开关 | 已有 ≥2 种真实取值需求 |
| 设计扩展点/插件机制 | 有明确的、已签约的第二使用场景 |
| 加缓存层 | 有实测的性能数据证明必要 |
| 引入设计模式 | 能用 20 行直线代码写清就先别用 |

## 明确禁止

- **"以防万一"式代码**：空 try-catch、永远不会触发的分支、没人调用的兜底函数
- **未来-proofing**：为不存在的第二个数据库、第二种认证方式、第二套主题预留抽象
- **过度分层**：controller → service → manager → handler → helper 五层调用，实际每层只做透传
- **复制式复用**：把一段代码复制到 utils 里然后两处都改一遍，不如先留两份重复

## 正确的顺序

```
第一处：写死，直接实现
第二处：复制一份（重复是可接受的）
第三处：此时模式才清晰，再抽象
```

三处之前抽象，你抽的是猜测；三处之后抽象，你抽的是事实。

## 报告要求

如果你认为某处确实需要抽象但不符合上述条件，**先说明你的理由并等待确认**，不要直接做。
