## Core Principles

### I. 简单优先（NON-NEGOTIABLE）

- 没有第二处调用点，不得抽公共层；没有第二个实现，不得定义接口。
- 初始实现模块数上限 <<3>> 个，超出需要书面说明理由。
- 禁止未来-proofing：不为不存在的第二个数据库、第二种认证方式预留抽象。
- 能用 20 行直线代码写清的，不得引入设计模式。

### II. 可测试性

- 核心业务逻辑必须可脱离框架与网络单独测试。
- 新增对外接口前先定义契约（输入、输出、错误码），再写实现。
- 测试必须覆盖错误路径，不只是 happy path。

### III. 依赖克制

- 引入任何新包必须说明：解决什么问题、为何不能用现有手段解决、传递依赖规模、许可证。
- 白名单见 `.claude/rules/02-dependencies.md`。
- 禁止引入职责重叠的同类库。

### IV. 模块边界

- 依赖方向严格单向：`<<api → domain → infra>>`，不得反向引用。
- 禁止 `utils/` / `common/` / `shared/` 这类无边界目录。
- 禁止用 `xxxV2` / `xxxNew` 命名文件绕过重构。

### V. 证据化交付

- 任何"完成"声明必须附带：执行的命令、实际输出、覆盖范围、残余风险。
- 禁止在未执行验证的情况下声称完成。
- 禁止通过修改测试使其通过，除非能证明原测试有误。

### VI. 可观测性

- 所有模块使用结构化日志。
- 外部调用（HTTP、数据库、消息队列）必须记录耗时与失败原因。
- 禁止空 try-catch 与静默失败。

## 0-1 阶段附加约束

- **范围纪律**：任何改动不得触碰本次任务范围外的文件；发现别处问题只报告。
- **提交纪律**：一个 task 一次 commit，保证随时可回滚到上一个可用状态。
- **不留残骸**：完成时清理调试代码、注释掉的代码块、不再被调用的旧函数。

## Governance

- 本宪法优先于其他一切实践约定。
- 修改宪法需：说明变更理由、团队确认、给出存量代码的迁移方案。
- 所有 plan 在生成前必须通过上述原则的合规检查；不通过的需求修订或在 plan 的复杂度追踪区记录例外。
